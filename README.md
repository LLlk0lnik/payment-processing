# Асинхронный процессинг платежей

FastAPI принимает платёж и сохраняет его вместе с событием outbox в PostgreSQL.
Отдельный relay публикует события в RabbitMQ. Один consumer эмулирует платёжный
шлюз, фиксирует результат и отправляет webhook.

## Запуск

Нужны Docker Engine и Docker Compose v2.

```sh
cp .env.example .env
docker compose up --build -d
docker compose logs -f consumer outbox
```

Миграции применяются отдельным одноразовым контейнером до старта приложения.
API: http://localhost:8000/docs. RabbitMQ: http://localhost:15672
(локальные учётные данные `payments` / `payments`). Поменяйте `API_KEY` в `.env`
перед использованием вне локального окружения. Данные хранятся в Docker volumes.

## API

Оба эндпоинта требуют `X-API-Key`. Для создания также нужен `Idempotency-Key`.

```sh
curl -i http://localhost:8000/api/v1/payments \
  -H 'X-API-Key: local-development-key' \
  -H 'Idempotency-Key: order-123' \
  -H 'Content-Type: application/json' \
  -d '{"amount":"1250.00","currency":"RUB","description":"Заказ 123","metadata":{"order_id":123},"webhook_url":"http://host.docker.internal:9000/webhook"}'
```

Ответ `202 Accepted`:

```json
{"payment_id":"c03c944f-36c4-45ca-9762-04182dffbcbd","status":"pending","created_at":"2026-10-29T12:00:00Z"}
```

```sh
curl http://localhost:8000/api/v1/payments/c03c944f-36c4-45ca-9762-04182dffbcbd \
  -H 'X-API-Key: local-development-key'
```

GET возвращает сумму строкой, валюту, описание, metadata, URL webhook,
ключ идемпотентности и даты.
Повтор POST с тем же ключом и эквивалентным телом возвращает существующий платёж
с текущим статусом. Другой запрос с тем же ключом получает `409`.
Неверный API-ключ — `401`, неверное тело или отсутствующий ключ идемпотентности —
`422`, неизвестный платёж — `404`. Поддерживаются RUB, USD, EUR; сумма положительная,
до 16 цифр в целой части и до двух знаков после запятой.

## Обработка и доставка

- Payment и outbox создаются в одной транзакции; уникальный индекс защищает от
  конкурентных запросов с одинаковым ключом.
- Relay блокирует неопубликованные строки через `FOR UPDATE SKIP LOCKED`.
  Отмечает событие опубликованным только после publisher confirm RabbitMQ.
  При недоступности брокера транзакция откатывается, публикация повторяется.
- Очереди durable, сообщения persistent. `payments.new` — основная очередь.
- Эмуляция шлюза занимает 2–5 секунд, результат успешен с вероятностью 90%.
  Бизнес-отказ `failed` — штатный результат, webhook отправляется и для него.
- Результат фиксируется перед HTTP-запросом. Повторная доставка не меняет уже
  обработанный платёж. Блокировка строки сериализует обработку дублей.
- Техническая ошибка обработки или любой неуспешный HTTP-ответ вызывает retry.
  Всего три попытки: первоначальная, через 1 секунду, через 2 секунды.
  Ожидание выполняют TTL-очереди `payments.new.retry.1` и `.2`.
  Они используют quorum и at-least-once dead lettering.
- После третьей ошибки событие попадает в `payments.dead`. Платёж сохраняет
  фактический результат шлюза: сбой уведомления не превращает успешный платёж в failed.
- Перед подтверждением исходного сообщения consumer дожидается подтверждения
  публикации retry/DLQ. При недоступности брокера исходное сообщение возвращается
  в очередь. Сбои инфраструктуры могут вызвать дополнительные доставки.

Гарантия — at-least-once. Авария между публикацией и commit outbox может породить
дубликат сообщения. Авария после приёма webhook клиентом, но до commit отметки
доставки может повторить webhook. Получатель должен дедуплицировать уведомления
по `Idempotency-Key`, равному payment_id. Для настоящего внешнего шлюза этот же
ключ нужно передавать провайдеру: локальная транзакция не обеспечивает exactly-once
для внешнего списания.

Webhook содержит `payment_id`, `amount`, `currency`, `status`, `metadata`,
`processed_at`. Успех — любой HTTP 2xx. Редиректы не выполняются. URL должен быть
доступен из контейнера consumer; `localhost` внутри контейнера указывает на него
самого. На Docker Desktop для сервиса на хосте используйте `host.docker.internal`.

DLQ просматривается в RabbitMQ UI. После устранения причины сообщение можно
вручную перепубликовать в `payments.new`, сбросив заголовок `attempt` в `1`.
Уже доставленный webhook повторно не отправится. Автоматического удаления
обработанных outbox-строк нет; для длительной эксплуатации нужна политика хранения.

Для сквозной проверки на Docker Desktop выполните `.venv/bin/python tests/smoke.py`
после запуска compose. Проверка поднимает временный HTTP-приёмник на порту 19090,
создаёт два платежа и проверяет webhook, интервалы retry и DLQ. Тестовые записи
и одно сообщение в DLQ остаются для просмотра.

## Структура

```text
app/
  api/             # HTTP, авторизация, создание платежей
  services/        # шлюз и webhook
  config.py        # настройки окружения
  db.py            # асинхронные сессии
  models.py        # таблицы
  schemas.py       # контракты запросов и событий
  messaging.py     # топология очередей
  main.py          # ASGI-приложение
  outbox.py        # relay
  worker.py        # единый consumer
migrations/        # Alembic
tests/             # проверки контрактов, retry и PostgreSQL
```

## Разработка и проверки

```sh
python3.12 -m venv .venv
. .venv/bin/activate
pip install -c constraints.txt -e '.[dev]'
pytest
ruff check .
```

Интеграционный тест требует отдельную PostgreSQL БД и `TEST_DATABASE_URL`
в формате `postgresql+asyncpg://user:password@localhost:5432/test_payments`.
Он создаёт временную схему, проверяет десять конкурентных запросов, единственный
платёж и outbox, конфликт ключа и GET; затем удаляет только эту схему.
Без переменной интеграционные тесты пропускаются. Unit-тесты не требуют брокера и БД.
Дополнительные интеграционные проверки
покрывают повтор webhook без повторной обработки шлюзом, откат outbox и связку
relay/consumer с тестовым брокером FastStream.

Проверка миграций:

```sh
docker compose run --rm migrate alembic check
docker compose logs --tail=100 api consumer outbox
```

Остановка: `docker compose down`. Команда `docker compose down -v` также удаляет
сохранённые платежи и очереди.
